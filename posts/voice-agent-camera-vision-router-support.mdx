> **TL;DR:** A support agent that can see is worth building, but streaming frames into the model all call long pays for thousands of images nobody needed. Make looking a tool: the model calls it when the answer depends on what the camera shows, and says why. Grab three frames a third of a second apart and send them as one side-by-side image, because one frame cannot tell a blinking light from a solid one. Have the vision model return structured light states, and let a plain Python table decide the fix. You can try it below with your own router or our drawn one.

"The internet light? It's kind of orange. Maybe yellow. Is it flashing? I think it's flashing."

Every ISP support line hears this sentence a few thousand times a day. The caller cannot describe the router, the agent cannot see it, and the call becomes twenty questions about colours. Asking the caller to point their phone at the router fixes the description problem in one second. The question is what it does to your bill and your latency.

This post walks through the [router rescue demo](https://github.com/mahimairaja/awesome-voice-apps/tree/main/demos/router-rescue) in awesome-voice-apps: a voice agent for a made-up provider, Northline Fibre, that reads router lights through the camera and walks the caller through the fix.

## The default: a frame every second

LiveKit Agents makes live video one flag. With a realtime model that accepts video, set `video_input=True` in `RoomOptions` and the session samples the caller's camera for you: by default [one frame per second while the user speaks and one every three seconds otherwise](https://docs.livekit.io/agents/models/realtime/plugins/gemini/), adjustable with a `video_sampler`.

That default is right for open-ended assistants, where anything on camera might matter. It is wrong for a support call, for three reasons:

1. **Most of the call is not about the picture.** Greeting, account check, "did you try turning it off", confirming the fix. In a two-minute call the router is relevant for maybe three moments.
2. **Every frame is billed as image input.** The [LiveKit video docs](https://docs.livekit.io/agents/multimodality/vision/video/) say it plainly: models consume tokens for each video frame, so higher frame rates increase cost. A frame a second over a 400-person outage queue adds up.
3. **It ties you to a realtime model with video support.** A cascaded pipeline (STT, LLM, TTS) has no live video path at all, and many production support agents are cascaded for cost and control.

The router agent turns the question around: instead of the camera pushing frames at the model, the model asks to look.

## Looking is a tool

The agent gets one tool for its eyes:

```python
@function_tool()
async def look_at_camera(self, context: RunContext, reason: str, focus: Focus = "lights") -> str:
    """Look at the caller's router through their camera, once.

    Only call this when the answer depends on what the router shows now.

    reason: why you need to look, in a few words (shown to the caller).
    focus: lights, label, or cables.
    """
```

Two details do most of the work.

**The `reason` argument.** The model has to say why it is looking before it can look. That string goes to the screen next to the frames ("confirm the power cycle fixed the internet light"), which makes the agent's decisions auditable by the caller and by you in a transcript review. It also nudges the model away from reflexive looking: writing a reason for "hello" is awkward, so it does not.

**The instructions frame looking as a cost.** The prompt says each look costs money and lists the three moments that justify one: the first diagnosis, checking a step the caller just did, and reading the label. The intended shape of a call is one look to diagnose, one to confirm the fix, and none during small talk.

The tool also guards itself, because a prompt is a request, not a limit:

```python
recent = self._looks[-1] if self._looks else None
if recent and recent["focus"] == focus and time.monotonic() - recent["at"] < REUSE_SECONDS:
    return "You looked a moment ago. " + self._summary(recent)
if len(self._looks) >= MAX_LOOKS:
    return "Look limit reached for this call. Work from what you already saw."
track = camera_track(self.room)
if track is None:
    return "Their camera is off. Ask them to turn it on and point it at the router."
```

A second look at the same thing within three seconds returns the first reading for free, a call is capped at six looks, and a missing camera comes back as a sentence the model can say instead of an exception.

## One frame cannot see a blink

The obvious version grabs a single frame. Point it at a router whose internet light blinks amber, the classic "no sync" fault, and the frame lands on the light or between flashes depending on timing. Between flashes, the photo honestly shows the light off, and the playbook sends the caller to check a cable that is fine. A blink is a signal in time, and a still photo has no time in it.

The fix is to sample a short burst and send it as one image:

```python
FRAMES = 3
FRAME_GAP = 0.35


async def sample_frames(track: rtc.RemoteVideoTrack, timeout: float = 2.0) -> list[Image.Image]:
    """Open the camera stream only for this look and keep three spaced frames."""
    stream = rtc.VideoStream(track, capacity=1)
    images: list[Image.Image] = []
    next_at = 0.0
    try:
        async with asyncio.timeout(timeout + FRAMES * FRAME_GAP):
            async for event in stream:
                now = time.monotonic()
                if now < next_at:
                    continue
                images.append(_to_image(event.frame))
                if len(images) == FRAMES:
                    break
                next_at = now + FRAME_GAP
    except TimeoutError:
        pass
    finally:
        await stream.aclose()
    return images
```

`rtc.VideoStream(track, capacity=1)` opens a reader on the caller's video track only for the duration of the look. The ring buffer holds one frame, so the reader always gets the newest one and never builds a backlog. When the look is done the reader closes.

Why three frames 0.35 seconds apart? Router status lights blink at roughly one to two hertz. Our sample router blinks on a 0.8 second cycle, 0.4 on and 0.4 off. Three samples spread over 0.7 seconds span more than either half of the cycle, so at least one frame lands on and at least one lands off. You can check that with a pencil: wherever the first sample falls, the span of three cannot fit inside a 0.4 second window.

Then the three frames become one contact strip:

```python
def contact_strip(images: list[Image.Image], tile: tuple[int, int], quality: int) -> bytes:
    """Lay frames left to right in one JPEG, so one image carries the timing."""
    strip = Image.new("RGB", (tile[0] * len(images), tile[1]))
    for i, image in enumerate(images):
        fitted = image.copy()
        fitted.thumbnail(tile)
        x = i * tile[0] + (tile[0] - fitted.width) // 2
        strip.paste(fitted, (x, (tile[1] - fitted.height) // 2))
    out = io.BytesIO()
    strip.save(out, format="JPEG", quality=quality)
    return out.getvalue()
```

One image request instead of three, and the prompt tells the vision model what it is looking at: "three frames side by side, left to right, about 0.35 seconds apart. A light that is on in some frames and off in others is blinking."

This is the part I would steal for any vision agent that watches a device: status LEDs, a payment terminal, a car dashboard warning light, a machine on a factory floor. If the state you care about changes over time, give the model time inside one image.

## The model reads, the table decides

The voice LLM never sees the image. A separate, short vision request (`gpt-4.1-mini`, `detail: low`, `store: False`) reads the strip and must answer in a strict JSON schema:

```python
STATES = (
    "off", "solid_green", "blinking_green", "solid_amber", "blinking_amber",
    "solid_red", "blinking_red", "solid_white", "blinking_white", "not_visible",
)
```

Every light (power, internet, Wi-Fi, LAN) has to be one of those ten values, plus whether a router is in view at all, any readable label text, and a short note. `not_visible` is a first-class answer, and the prompt says "never guess".

What the lights *mean* is not the model's job. A plain function maps the reading to one playbook entry, most severe first:

```python
def diagnose(reading: dict) -> str:
    """Map a light reading to one playbook entry, most severe first."""
    if not reading.get("router_visible"):
        return "no_router"
    lights = reading.get("lights", {})
    power, internet, wifi = (lights.get(k, "not_visible") for k in ("power", "internet", "wifi"))
    if power == "off":
        return "no_power"
    if power.endswith("_red"):
        return "hardware_fault"
    if power.startswith("blinking"):
        return "booting"
    if internet == "off":
        return "no_line"
    if internet.endswith("_amber"):
        return "no_sync"
    if internet.endswith("_red"):
        return "outage"
    if wifi == "off":
        return "wifi_off"
    healthy = ("solid_green", "blinking_green", "solid_white", "blinking_white")
    if power in healthy and internet in healthy:
        return "healthy"
    return "unclear"
```

The tool returns the reading, the diagnosis and the next step from the playbook, and the voice model's job shrinks to saying it well. This is the same split that runs through every agent we ship for clients: the model handles language and perception, code handles the decision. It has three practical payoffs:

- **The advice never drifts.** Your support team owns the playbook. Changing "power cycle for 10 seconds" to 30 is a one-line diff with a test, not a prompt experiment.
- **Every branch is unit-testable without a camera or an API key.** The demo's tests feed `diagnose()` ten readings and check ten outcomes.
- **Perception errors are visible.** When the agent gives a wrong fix, the panel shows whether the model misread the light or the playbook was wrong. Those need different fixes, and a single end-to-end prompt hides which one you have.

That gap is the whole argument of this post in one number.

A few things about how it runs in the playground, because they matter in production too:

- **The camera grant is per demo.** The site mints a LiveKit token that allows only the microphone for every other demo. The router demo's token adds the camera source and nothing else; the visitor still cannot publish data.
- **The look gets a hold line.** Sampling plus a vision request takes a second or two. The tool starts `session.say("One sec, looking.", add_to_chat_ctx=False)` without awaiting it, and calls `context.disallow_interruptions()` so the result is still spoken if the caller talks over the hold line. That is the pattern from the [LiveKit audio customization docs](https://docs.livekit.io/agents/multimodality/audio/customization/).
- **The vision call is billed to the call.** VoiceGateway meters the session's STT, LLM and TTS automatically, but it never sees a direct OpenAI request. The hosted agent adds each look's token usage to the call's cost record itself, so the budget guard and the cost panel include vision.
- **Frames are never written down.** They exist in worker memory for the length of one look, go to the vision request with `store: False`, and reach the browser as a byte stream that lives only in that tab.

## Where it falls short

A camera on a dim shelf with a lamp behind the router produces a strip of glare, and `not_visible` comes back for half the lights. The playbook handles that ("move closer and dim any bright light behind the router") rather than guessing, but it costs a look. Real deployments should check exposure before spending a vision request on a frame that is mostly black.

Router models also differ. Our playbook is for one fictional router with four labelled lights. A real ISP has a dozen models with different light layouts and colours, so the vision prompt should be told the model first, which is exactly what the `label` focus is for: read the sticker, then load that model's light map.

## What this means for you

1. **Make perception a tool call with a reason.** If your agent can see, let it decide when to look and make it say why. You get lower cost, a readable audit trail, and a natural place to enforce limits.
2. **Put time inside the image when state changes over time.** Blinks, progress bars, gauges and screens that cycle all need more than one frame. A side-by-side strip costs one image request.
3. **Keep the decision in code.** Have the vision model return a fixed vocabulary, and map it to actions with a function your domain experts can read and you can test.
