WebRTC is why a browser tab can open your microphone and hold a live call without a plugin. The name covers two things at once. [WebRTC for the Curious](https://webrtcforthecurious.com/), the open book written by WebRTC implementers, compares them to the web you already know: the WebRTC protocol is like HTTP, and the WebRTC API is like `fetch`. Very little underneath is new. A WebRTC agent orchestrates protocols that date back to the early 2000s, and every call walks through four steps in order: signalling, connecting, securing and communicating. If one step fails, the next one never starts.

Signalling comes first, because two peers must agree on what the call is before they can share it. One side writes an offer and the other replies with an answer. Both are Session Description Protocol text, plain key and value lines that list the codecs each side supports, the addresses where it can be reached, and the fingerprint of its security certificate. WebRTC does not say how this text travels. A WebSocket is the usual choice, but a REST endpoint works just as well. The designers left signalling out on purpose, because SIP had already solved it.

Connecting is the hard part. Most devices sit behind NAT, so a laptop does not know the address the rest of the internet sees for it. [ICE](https://webrtcforthecurious.com/docs/03-connecting/) solves this. Each side gathers candidates, meaning the ways it might be reached: its local address, the public address a STUN server reports back to it, and, when needed, a relay address on a TURN server. ICE pairs every local candidate with every remote one, so three on each side make nine pairs. It sends connectivity checks across each pair and nominates one that works. TURN is the fallback when no direct path exists, and the media then flows through the relay.

Every WebRTC connection is authenticated and encrypted. Once a path exists, the peers run a DTLS handshake, which is TLS adapted for UDP. Each side checks that the certificate it received matches the fingerprint from the offer or answer. The keys from that handshake then start SRTP, which encrypts the media itself. The weak spot is signalling. WebRTC cannot tell whether someone changed the session description on its way across, so the signalling channel needs protection of its own.

Media travels as RTP packets. Each stream is identified by an SSRC, and RTCP runs alongside to carry reports and feedback. WebRTC is codec agnostic, so the offer and answer settle on one: Opus is common for voice, VP8 and H.264 for video. Networks deliver packets late, out of order, or not at all, so the receiver holds them briefly in a jitter buffer to smooth playback. That buffer is a trade. It hides uneven arrival, and it adds a little delay to every packet that arrives early.

The book's rule for the next part is blunt: if your data is late, it is useless. WebRTC rarely waits for a perfect stream. A receiver can send a NACK asking for one missing packet again. A sender can add forward error correction, redundant data that rebuilds a loss without a round trip, and when loss is steady that is the lower-latency choice. A congestion controller estimates the available bandwidth. In Google Congestion Control, the most widely deployed one, loss above 10% lowers the estimate and loss below 2% raises it. When bandwidth falls, the sender lowers quality instead of stalling the call.

Not everything is audio or video. Data channels carry arbitrary messages over SCTP, inside the same DTLS connection, and start only when one side asks for one. They are ordered and reliable by default, and can be set to behave like UDP. Calls with more than two people change the shape. A full mesh connects everyone to everyone and is best kept to small groups. A selective forwarding unit, or SFU, receives each participant's media and forwards it to the others. An MCU goes further and re-encodes everything into a single feed. The book is honest about the SFU: a simple one takes a weekend, and a good one is never finished.

A voice agent uses this same machinery with a server on the far end. The agent joins as another peer, often through an SFU, and every step above sits between a caller's sentence and the reply. When a call misbehaves, `chrome://webrtc-internals` in Chrome, or `about:webrtc` in Firefox, shows the selected candidate pair, packet loss, NACK counts and jitter buffer delay.
