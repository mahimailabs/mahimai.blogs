Our 12-utterance smoke run completed every stage of a text-to-speech benchmark: synthesise the prompt, transform the audio, transcribe it, and score the transcript. Two synthesis systems, four audio conditions, neatly formatted scores. It looked ready for a larger run.

The sample contained only digits.

Once we fixed the selection, the scores started moving. A difference of one recognised word was enough to reverse the ordering. Then a scoring fix landed while the larger run was already running, and the process kept using the old code.

These failures need different checks: **inspect the sample, keep the error counts, and record which scorer produced them**. A successful process exit can't tell you any of that.

## Sample Coverage

The first smoke run selected the beginning of a category-sorted corpus:

```python
utterances = loader.load()[:limit]
```

The first 60 entries in [handset-bench's text set](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/src/handset_bench/textset/dialtone_v1.jsonl) are digit prompts. Taking twelve of them never exercises the other five categories: proper nouns, addresses, dates/times/money, conversational text, and general text.

The early output reported 7.09% word error rate (WER) in every condition for both Piper and ZipVoice-Distill. That repetition was a useful reason to investigate. It wasn't proof that the audio transform was broken: different recordings can produce the same transcript, error count, or rounded percentage.

Checking the selected IDs exposed the coverage problem. The project's [round-robin sampler](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/src/handset_bench/textset/loader.py#L84-L109) spreads a small run across categories:

```python
utterances = loader.sample(loader.load(), 12)
# Two utterances from each of six categories.
```

<SamplingCollapse />

This gives each category a chance to fail. It does **not** reproduce the full corpus's category proportions, and two examples can't establish performance within a category. It's a coverage check before committing to a larger run.

## Metric Resolution

The revised smoke run had 114 reference words after normalisation. These are the error counts recorded in the original debugging write-up:

| Audio condition  | Piper errors | ZipVoice-Distill errors |
| ---------------- | -----------: | ----------------------: |
| Wideband control |            2 |                       0 |
| Clean G.711      |            1 |                       1 |
| 1% packet loss   |            2 |                       4 |
| 3% packet loss   |            1 |                       2 |

Here, “errors” means substitutions plus deletions plus insertions. Corpus WER divides that total by the total reference-word count; it isn't the average of each utterance's percentage. The project's [WER implementation](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/src/handset_bench/metrics/wer.py) uses this aggregation.

One error in this sample changes WER by **100 / 114 = 0.877 percentage points**. Piper's 1.75% versus 0.88% is two errors versus one. Reporting two decimal places doesn't create more evidence.

<BenchmarkResolution />

The 300-utterance corpus has 2,904 reference words under the checked normaliser, so its one-error increment is about 0.034 percentage points. That is finer numerical resolution, **not a confidence interval or a guarantee that a ranking will hold**. The result still depends on which utterances, voices, recordings, and loss realisations you evaluated.

These small-run numbers are historical debugging observations, not a current model leaderboard. The original smoke-run manifests aren't available with this article; the public implementation and retained larger-run records support the sampling and denominator checks, not a fresh reproduction of that table.

## Loss Ordering

More packet loss does not force WER to increase on every clip or small sample. Recognition is a separate transformation of the damaged audio. A changed sound can produce fewer word errors, even when the audio has lost more information.

The earlier version of this article claimed that the 3% condition removed every frame removed by the 1% condition, plus more. The implementation doesn't do that: its random seed includes the **condition name**, so the two conditions use different draws. They can lose different parts of a sentence. The [codec implementation](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/src/handset_bench/codec.py) makes that distinction explicit.

Even deliberately nested masks would constrain the missing frames, not the recogniser's error count. The [published full-run findings](https://github.com/mahimairaja/DialTone-TTS/blob/28a1536da3f5749c904ec549616706a999856de9/docs/baseline-findings.md) contain the same reversal: ZipVoice scores 4.34% WER at 1% loss and 4.30% at 3%. That directly contradicts the original rule.

A reversed score is a prompt to inspect the changed transcripts. To isolate the loss effect, hold the source recording fixed, save the masks or their seeds, and repeat across loss realisations. Check the transformation itself for dropped-frame counts. Don't use the expected WER ordering as a substitute for that check.

For the audio side of this experiment, see [the PyTorch phone-line implementation](/blog/building-a-phone-line-in-pytorch). For a live receiver, [WebRTC jitter buffering](/blog/how-your-voice-travels-through-webrtc#jitter-buffering) adds playout deadlines and concealment that an offline loss mask doesn't reproduce.

## Run Provenance

Editing a Python file doesn't update a module already imported by an ordinary running process. Python normally checks its module cache on import; [its import documentation](https://docs.python.org/3/reference/import.html#the-module-cache) describes that behaviour.

We changed the text normaliser after a 300-utterance run had started. That process continued scoring with the version it had loaded earlier. Its output looked normal because, from the process's point of view, nothing had changed.

The costly mistake was saving only derived scores. Without the raw hypotheses, a correction to [digit normalisation](/blog/the-normaliser-that-scored-itself) required recognition to run again.

<TranscriptProvenance />

Keep the raw reference and hypothesis, utterance ID, condition, model identity, and scorer revision with each result. Retain the source audio or a stable reference to it when you need to investigate recognition itself. A cached transcript lets you change text scoring; it cannot test a different recogniser or repair missing audio.

For records containing transcripts, the project's [rescoring command](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/src/handset_bench/rescore.py) supports a dry run before overwriting results:

```bash
# Inspect the rescored output without changing records.
handset-bench rescore --results results

# Archive the original records before writing new scores.
handset-bench rescore --results results --write
```

The Modal scoring path stores these transcripts; the generic runner currently does not. Check the actual record before relying on rescoring. The command also leaves the existing revision metadata unchanged, so record the new scoring revision alongside the rescored output.

Pin the code revision at launch. If a scoring fix arrives during a run, either restart with the fix or finish collecting reusable transcripts and rescore them explicitly. Record both revisions so the resulting number has a traceable origin.

## Promotion Checks

Before a smoke run earns a larger run, its output should answer these questions:

| Check                                          | Evidence to keep                                                 |
| ---------------------------------------------- | ---------------------------------------------------------------- |
| Did every intended category run?               | Selected utterance IDs and category counts.                      |
| Did the audio conditions differ as configured? | Audio hashes, transform settings, realised loss counts.          |
| What moved the score?                          | Substitutions, deletions, insertions, and reference-word totals. |
| Can this score be reproduced?                  | Input, model, seed, and scorer identities.                       |
| Can scoring be fixed cheaply?                  | Raw references and hypotheses, saved before normalisation.       |

A smoke run has done its job when it exposes broken wiring and missing coverage. A model comparison needs a separate argument about the sample and the uncertainty. Keep that distinction visible in the report, and keep the transcripts that let you revisit it.
