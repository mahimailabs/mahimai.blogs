“Six one three five five five zero one nine eight” and `613 555 0198` describe the same phone number. Put those strings through the English normaliser used in our benchmark, then calculate word error rate: **300%**.

No audio is needed to reproduce this failure. The scoring pipeline changes the representation before it measures the difference.

That matters in a [telephone-channel benchmark](/blog/building-a-phone-line-in-pytorch): a text-processing mismatch can look like damage to the voice. The fix starts with a scoring contract. Decide which differences are formatting, which change the identifier, and which must survive normalisation.

<span id="the-first-layer" aria-hidden="true" />

## Token Alignment

WER counts substitutions, deletions, and insertions, then divides by the number of reference tokens. The English normaliser can turn a sequence of spoken digits into one token while leaving a grouped numeric transcript as several tokens.

<NormaliserFailure />

For this pair, the alignment has one substitution and two insertions against one reference token: **(1 + 0 + 2) / 1 = 3**, or 300%. WER can exceed 100% because insertions add errors without increasing the reference denominator. [JiWER's alignment tools](https://jitsi.github.io/jiwer/usage/#alignment) expose the counts behind that percentage.

The reproduced fixture uses the Whisper-derived `whisper-normalizer 0.1.15` package and `jiwer 4.0.0`. It verifies a text-scoring failure, not the quality of a particular recording or every Whisper release. You can run the <a href={validationScript} download="verify-normaliser.py">complete fixture</a> and inspect its <a href={validationOutput}>recorded output</a>.

<span id="the-second-layer-leading-zeros" aria-hidden="true" />

## Leading Zeros

A phone number is an identifier. Treating each group as an integer deletes information: `0198` becomes `198`, and `007` becomes `7`.

| Input  | Stock normaliser output |
| ------ | ----------------------- |
| `0198` | `198`                   |
| `007`  | `7`                     |
| `0500` | `500`                   |

Splitting digits **after** this transformation is too late. You can split `198` into `1 9 8`, but you can't infer that a zero used to lead it.

The benchmark's wrapper separates numeric digits before normalisation, then separates and maps them again afterwards. Both passes matter because written digits and spoken number words enter through different paths.

<span id="the-third-layer-brackets" aria-hidden="true" />

## Bracket Removal

The stock normaliser treats parenthesised text as an annotation. In the phone-number fixture, `(613) 555-0198` becomes `555 198`: the area code disappears along with the leading zero.

The [Whisper normaliser source](https://github.com/openai/whisper/blob/v20250625/whisper/normalizers/english.py) shows the parenthesis-removal rule. That is a reasonable convention for annotations such as `(inaudible)`, but it conflicts with telephone-number formatting.

For the benchmark's chosen policy, the wrapper removes bracket characters while preserving their contents. This protects the area code. It also changes how annotations elsewhere are handled, so it shouldn't be applied blindly to every transcript format.

## Scoring Policy

For the tested English phone-number forms, we want the same ten digit tokens. A formatting change should score zero; a changed digit should remain an error.

<NormaliserConvergence />

The [versioned implementation](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/src/handset_bench/metrics/wer.py) first matches a complete lowercase numeric ordinal, otherwise a single digit:

```python
import re

DIGITS = re.compile(r"\d+(?:st|nd|rd|th)\b|\d")
assert DIGITS.findall("007 on the 1st") == ["0", "0", "7", "1st"]
```

That pattern explains why `007` can be separated without turning `1st` into `1 st`. The complete wrapper also handles bracket delimiters, punctuation, digit words, and meridiem spacing. Its behaviour belongs to this benchmark's policy; it is not a universal definition of correct speech.

In particular, the wrapper is too permissive for some transactional fields. In the reproduced fixture, `€12` and `12` both become `1 2`. Removing punctuation can erase currency or decimal distinctions. Amounts need their currency and decimal value; times need their clock convention; mixed letter-and-digit codes need an explicit character policy. Use separate field checks when those distinctions determine whether an action is correct.

Digit-token WER is useful for locating mistakes. Also report **whole-identifier exact match after the agreed field normalisation**: one substitution in a ten-digit phone number is 10% digit-token WER, but the phone number is still wrong. Neither metric should hide the other.

<span id="the-part-that-should-worry-you" aria-hidden="true" />

## Regression Tests

A normaliser needs tests for both equivalence and difference. A function that deletes every digit would make the formatting examples agree while destroying the task.

| Test                                  | Required result                                            |
| ------------------------------------- | ---------------------------------------------------------- |
| Spoken digits vs grouped phone number | Same digit sequence.                                       |
| Bracketed vs unbracketed area code    | Same phone identifier.                                     |
| `007` vs `7`                          | Different identifiers.                                     |
| One wrong digit                       | A nonzero edit count and failed exact match.               |
| `first` vs `1st`                      | Equivalent under the chosen ordinal policy.                |
| Currency, decimals, annotations       | Explicit field-specific fixtures, not assumed equivalence. |

The [project's regression tests](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/tests/test_wer.py) cover the number-format cases. The downloadable fixture also records counterexamples outside that scope, so passing the phone-number examples doesn't look like a general guarantee.

Pin the normaliser version and keep the raw reference and hypothesis alongside the normalised tokens. Changing the policy changes both the alignment and, potentially, the denominator. Recompute both sides of a comparison under the same policy before comparing scores.

[A smoke run](/blog/your-smoke-run-is-lying-to-you#run-provenance) should check these fixtures before expensive recognition runs. The [audio receive path](/blog/how-your-voice-travels-through-webrtc#pipeline-diagnostics) needs its own evidence. Keeping the text boundary inspectable lets you tell a lost digit in the sound from a lost digit in the scorer.
