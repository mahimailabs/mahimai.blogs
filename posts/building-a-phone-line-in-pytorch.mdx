A voice that sounds clear through headphones can lose useful detail on a telephone connection. Before testing recognition, we need a repeatable way to change the audio.

The [handset-bench channel model](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/src/handset_bench/codec.py) does that in PyTorch: filter the signal, resample to 8 kHz, quantise it, and erase selected frames. You can inspect every stage and reuse the same configuration in training and evaluation.

It is an **offline approximation**. TorchAudio's mu-law transform isn't a byte-compatible G.711 encoder, and silence-filled frames don't reproduce a live receiver's packet-loss concealment. Those boundaries matter when interpreting the result.

## Signal Path

The function accepts a waveform and its actual sample rate, then returns floating-point audio at 8 kHz:

```python
from handset_bench.codec import phone_line

# wav: mono float32 PCM, scaled to [-1, 1], sampled at 24 kHz.
narrow = phone_line(wav, src_sr=24000, loss_p=0.03, seed=7)
```

<SignalChain />

Filtering at the source rate suppresses unwanted frequencies before downsampling. The model uses 300 Hz high-pass and 3,400 Hz low-pass cascades, followed by TorchAudio's [sinc-based resampler](https://docs.pytorch.org/audio/2.8/generated/torchaudio.transforms.Resample.html).

A cutoff below the 4 kHz output Nyquist frequency doesn't guarantee zero aliasing. The filter has a transition band, and the resampler has its own low-pass kernel. Inspect their combined response at the source rates you actually use.

Pass mono audio deliberately. This implementation flattens multidimensional tensors; passing stereo channels directly would concatenate them rather than downmix them.

<span id="one-biquad-is-not-a-carrier" aria-hidden="true" />

## Filter Design

Four low-pass sections need four different Q values to form an eighth-order Butterworth response. Repeating one section four times makes a steeper filter, but also compounds its attenuation at the intended cutoff.

The project calculates the section values like this:

```python
import math

order = 8
qs = tuple(
    1 / (2 * math.cos((2 * k + 1) * math.pi / (2 * order)))
    for k in range(order // 2)
)
# Approximately: 0.510, 0.601, 0.900, 2.563.
```

<FilterRolloff />

The chart evaluates the small-signal digital low-pass coefficients at a **24 kHz source rate and 3,400 Hz cutoff**. One section gives about −13.08 dB at 6 kHz; the correctly tuned cascade gives −51.44 dB. Four identical Q = 1/√2 sections reach −12.04 dB at the intended cutoff, shifting their combined half-power cutoff to about 2,328 Hz. This coefficient response assumes no clipping; large signals can encounter TorchAudio's output clamping.

These are responses of the specified filter, not measurements of a carrier network or a claim of G.712 compliance. The earlier version of this post quoted different attenuation values without enough fixture detail; the chart now uses the actual digital response.

For a waveform test, measure a steady portion of a sine tone after the IIR startup transient. A peak over the whole buffer answers a different question. The project's [codec tests](https://github.com/mahimailabs/handset-bench/blob/651ce772ba08ab56dd1b057d3b2ac9304c6eeb4a/tests/test_codec.py) demonstrate that separation.

## Codec Fidelity

TorchAudio applies a continuous mu-law companding function and quantises the result into 256 levels. Its [encoding API](https://docs.pytorch.org/audio/2.8/generated/torchaudio.functional.mu_law_encoding.html) specifies that operation; it doesn't promise interoperable G.711 bytes.

For **this TorchAudio transform**, zero encodes to integer 128 and decoding that value yields approximately +0.00008621, or −81.29 dB relative to full scale. That small offset is a property of this quantiser. It is not evidence that telephone PCMU has no zero code.

G.711 PCMU uses its own codeword mapping. [RFC 3551](https://www.rfc-editor.org/rfc/rfc3551.html#section-4.5.14) specifies its 8-bit samples and RTP byte layout. If you need wire compatibility, use a G.711 implementation and test known encode/decode vectors. Matching TorchAudio only verifies compatibility with TorchAudio.

## Packet Loss

At 8 kHz, 20 ms contains **160 samples**. The model groups encoded values into blocks of that size and independently selects blocks for replacement. A probability of 3% is a random loss rate, not a promise that exactly 3% of a short clip will be erased.

Replacement with the model's silence code is a receiver policy layered on top of the loss decision. A network loses a packet; it doesn't deliver a packet full of silence. A live receiver might conceal the gap by repeating or synthesising audio. [WebRTC's receive path](/blog/how-your-voice-travels-through-webrtc#jitter-buffering) also includes arrival deadlines that this offline transform doesn't model.

The implementation preserves any trailing block shorter than 160 samples. That is a test-harness convention, not a rule about what a jitter buffer can lose. Keep the seed, realised mask, and tail policy with the result.

## Surrogate Gradients

Quantisation blocks the useful derivative needed for training. A straight-through estimator chooses a substitute gradient while retaining the quantised audio in the forward pass. The substitute is a training decision, not the true derivative of the codec.

For the **samplewise encode/decode stage**, a small custom autograd function makes that choice explicit:

```python
import torch
from handset_bench import codec

class CodecSTE(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        return codec.mu_law_decode(codec.mu_law_encode(x))

    @staticmethod
    def backward(ctx, grad_output):
        return grad_output

quantised = CodecSTE.apply(narrowband_pcm)
```

The forward pass calls the shared reference implementation directly. The backward pass deliberately treats this stage as an identity. This follows PyTorch's [custom autograd interface](https://docs.pytorch.org/docs/2.8/notes/extending.html#extending-torch-autograd).

It doesn't make the whole phone line an identity. Filters and resampling transform gradients; resampling also changes the number of samples. A loss mask needs its own gradient policy. Keep those operations outside this samplewise wrapper and verify both forward outputs and backward behaviour.

## Verification Tests

A shared function prevents training and evaluation from silently using different arithmetic. It doesn't prove that the shared function models the deployment channel correctly. Test those two claims separately.

| Boundary     | Check                                                                |
| ------------ | -------------------------------------------------------------------- |
| Input        | Mono layout, declared sample rate, amplitude range.                  |
| Filters      | In-band gain, cutoff response, stop-band attenuation after settling. |
| Resampling   | Expected output length and alias rejection at each source rate.      |
| Quantisation | Reference outputs and silence mapping; G.711 vectors if required.    |
| Loss         | Whole-frame masks, repeatability, realised rate, tail handling.      |
| Training     | Forward equality with the chosen reference and intended gradients.   |

The <a href={validationScript} download="verify-channel.py">validation script</a> and <a href={validationOutput}>recorded output</a> reproduce the filter, zero-code, and gradient checks with Python 3.12 and Torch/TorchAudio 2.8 on CPU. The custom wrapper matched the reference on 2,000,001 float32 inputs and returned the intended unit gradients. That checks this fixture, not every possible input or device.

Only then score the output. [A small smoke run](/blog/your-smoke-run-is-lying-to-you) can confirm coverage and execution; it can't establish a model ranking. And [the text normaliser](/blog/the-normaliser-that-scored-itself) needs its own fixtures, because an audio test can pass while the scorer still destroys a phone number.
